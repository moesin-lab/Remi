## Scope and evidence

Measured on 2026-11-23 with Bun 1.3.14 on isolated in-memory SQLite fixtures against base commit `d69bc1d46` (branch `agent/MUL-331`). These measurements are isolated local fixture samples, not production PostgreSQL latency or p95 claims.

## Root cause and change

Previously `packages/server/src/store/repos/issues-repo.ts` (`searchIssues` / `searchIssueCommentSnippet`):
1. Called `this.listIssues({ includeArchived: true })` without a `workspaceId`, loading and hydrating labels for every issue across **all workspaces**.
2. When `includeCommentBodies !== false`, ran a synchronous `SELECT body FROM multiremi_issue_message_records WHERE issue_id = ? ORDER BY created_at DESC` for **every issue row across all workspaces** (N+1 round-trips over the synchronous PG bridge).

With this change:
1. **Workspace & closed/archived pushdown**: Queries filter `i.workspace_id = ?` in SQL. When `!includeClosed`, SQL strips all 25 ECMAScript `WhiteSpace + LineTerminator` code points (`TRIM(COALESCE(i.status, 'todo'), <25 chars>)` on SQLite, `BTRIM(COALESCE(i.status, 'todo'), <25 chars>)` on PostgreSQL) before `NOT IN ('done', 'cancelled')`, matching `normalizeIssueStatus`'s JS `.trim()`, and gates archived exemption on `(TYPEOF(i.archived_at) = 'text' AND i.archived_at <> '')` on SQLite / `(i.archived_at IS NOT NULL AND i.archived_at <> '')` on PostgreSQL, matching `nullableString(row.archived_at)` and preserving the exact legacy rule (`if (!includeClosed && CLOSED_ISSUE_STATUSES.has(issue.status) && !issue.archivedAt) return false`).
2. **Portable literal-substring, Unicode/noncharacter/pattern-length guards & SQLite encoding/BLOB fallback**: Multi-word whitespace-separated terms are lowercased, deduplicated, escaped for `\`, `%`, `_`, and matched with `LOWER(...) LIKE ? ESCAPE '\'` across effective issue key (`issue_key` / `MUL-<issue_number>` / `id`), `title`, `description`, and comment `body_md`. Before `LOWER(...)`, columns conditionally normalize the only two non-ASCII Unicode code points whose ECMAScript `.toLowerCase()` produces ASCII or uncased characters (`U+212A` `'K'` -> `'k'` when any term contains `'k'`, and `U+0130` `'İ'` -> `'i\u0307'` when any term contains `'i'` or `'\u0307'`) so SQLite (`LOWER` is ASCII-only) and PostgreSQL (`en_US.utf8` `LOWER('İ')` drops `\u0307`) match JS `searchMatch()` identically in both directions (including standalone `"\u0307"` / `"\u0307stan"` queries against `"İstanbul"`). `buildIssueSearchResult` also requires `matchedCommentSnippet !== null` before assigning `matchSource = "comment"`. `canPushLike` additionally routes queries to the workspace-scoped JS fallback whenever: (i) any term has non-ASCII cased letters or `> 50` distinct terms, (ii) the query contains surrogate code units (`U+D800..U+DFFF`) on either backend, (iii) on SQLite, the query contains `U+FFFD..U+FFFF` (preventing SQLite `sqlite3Utf8Read` from folding `U+FFFE`/`U+FFFF` into `U+FFFD` during `LIKE`, which would inflate `total` / `X-Total-Count` and empty page 1), or (iv) any escaped `LIKE` pattern exceeds `ISSUE_SEARCH_MAX_SQL_PATTERN_BYTES = 4096` UTF-8 bytes (preventing SQLite's 50 KB `LIKE or GLOB pattern too complex` HTTP 500 on long valid queries). For embedded `U+0000` (NUL), UTF-16 reversed BOM (`U+FFFE`), and historical SQLite `BLOB` columns: queries containing `\u0000` return `{ issues: [], total: 0 }` immediately on PostgreSQL (where `TEXT` cannot store `0x00` and UTF-8 bind params reject NUL) and fall back to the workspace-scoped scan on SQLite; on SQLite, the single candidate SQL piggybacks `needs_fallback` checks across `id`/`issue_key`/`title`/`description` and shown comment `body_md`—character-level `INSTR(..., CHAR(0)) > 0`, UTF-16 reversed-BOM prefix detection via `HEX(SUBSTR(CAST(... AS BLOB), 1, 2))` (`'FEFF'` on `UTF-16le` / `'FFFE'` on `UTF-16be`, avoiding `X'...'` hex literals), and `TYPEOF(...) = 'blob'`—falling back within the same read snapshot only when such rows exist (zero extra SQL on normal workspaces). Fallback business read counts distinguish two entry paths: (a) queries that enter the workspace-scoped scan directly (non-ASCII cased letters such as `café`, `> 50` distinct terms, `> 4096 B` escaped patterns, surrogate/`U+FFFD..U+FFFF` guards, or SQLite query terms containing `\u0000`) run **1–5 business read SQL statements (`0` writes)** when visible comments are strictly `< batchLimit` (`<= 1999` under default 64 MiB budget), encoded batch size `<= budgetBytes`, and no single comment triggers oversized chunking—for example, when a workspace has both title-matched and comment-only issues and `q="café"&limit=1`, the fallback runs 5 business reads (1 `multiremi_issues` scan + 1 `nonFieldMatchedIds` comment scan + 2 page issue & label hydration reads + 1 page `fieldMatchedIds` comment-snippet scan; PostgreSQL additionally runs 1 read-only snapshot transaction-control statement); at **exactly `2000`** visible short comments (`batchRows.length === batchLimit`), `scanIssueCommentsBounded` issues **1 additional empty continuation probe**, bringing that mixed `q="café"` case from `5` to **`6` business reads (`0` writes)** (up to `6` reads); (b) ordinary ASCII queries that detect persisted SQLite `U+0000` / UTF-16 reversed BOM / `BLOB` via `needs_fallback = 1` during the candidate query and fall back within the same read snapshot run **1 candidate probe read + 1–5 fallback reads = 2–6 business read SQL statements (`0` writes)** under `< 2000` single-batch comments (e.g., a mixed field-hit + comment-hit fixture encountering persisted NUL executes `1 + 5 = 6` business reads, `0` writes). When row/byte cursor continuation (`>= batchLimit` rows or `> budgetBytes`) or oversized-comment `SUBSTR` chunking triggers, additional bounded continuation reads scale with batches/chunks rather than total issue count `N` (no per-issue N+1).
3. **Single-scan `workspace_issues AS MATERIALIZED` + `matched_comments AS MATERIALIZED` + PG `CROSS JOIN LATERAL (... LIMIT 1)`**: When `includeCommentBodies` is enabled, the candidate query materializes `workspace_issues AS MATERIALIZED` once per workspace (computing `match_rank` and database-native `ROW_NUMBER() OVER (ORDER BY i.updated_at DESC, <i.id | i.rowid> ASC) AS issue_ord`, scanning `multiremi_issues` once instead of 3 times and binding `workspace_id` once). Comment matching runs in `matched_comments AS MATERIALIZED` and combines with `workspace_issues` via `UNION ALL` instead of `LEFT JOIN`, preventing PostgreSQL 12+ from inlining a single-reference CTE into a correlated Nested Loop when table statistics are stale (`reltuples = 0` after bulk inserts). On PostgreSQL (`dialect === "postgres"`), `matched_comments` uses `CROSS JOIN LATERAL (SELECT 1 AS hit FROM multiremi_conversation_log l WHERE l.session_id = s.id AND l.visibility = 'shown' AND l.kind = 'message' AND l.deleted_at IS NULL AND (...) LIMIT 1) cm`: keeping `l.session_id = s.id` inside a `LIMIT 1` subquery prevents subquery pull-up and forces the planner to keep `session_id = s.id` as a base restriction (`Index Cond: (...session_id = s.id...)`) rather than scanning `multiremi_conversation_log` via an unparameterized partial index with a `Join Filter` when `reltuples = 0`, short-circuiting on the first matching comment per session. On SQLite, `matched_comments` joins `workspace_issues wi -> multiremi_issue_sessions s -> multiremi_conversation_log l` directly (using `idx_multiremi_conversation_log_window`). JS merges both `UNION ALL` branches by `id` (`matchRank = Math.min(...)`, `hasCommentMatch = a || b`), keeping `miss = 1 SQL` and preserving `matchedCommentSnippet` on key/title/description hits.
4. **Page-only hydration, native-collation candidate tie-breaking & comment tie-breaking contracts**: Both SQL pushdown (`includeCommentBodies: true/false`) and non-ASCII fallback paths derive `issue_ord` from database-native `ORDER BY i.updated_at DESC, <i.id | i.rowid> ASC` (`ROW_NUMBER() OVER (...)` in SQL pushdown and explicit `ORDER BY` row index in fallback). `compareIssueSearchCandidates` orders by `matchRank ASC`, `Date.parse(right.updatedAt) - Date.parse(left.updatedAt)` (falling through on `0` / `NaN`), then `left.issueOrd - right.issueOrd` (with `id ASC` fallback)—removing JS UTF-16 code-unit comparison on `updatedAt`. Equal-instant ISO variants with distinct text (e.g., `2026-01-01T13:00:00+01:00` vs `2026-01-01T13:00:00.000+01:00`) follow the database's native `ORDER BY updated_at DESC` collation (SQLite `BINARY`, PostgreSQL locale collation such as `en_US.utf8`). For **exact identical `updated_at` strings**, SQLite uses `i.rowid ASC` (matching legacy SQLite scan order), while PostgreSQL explicitly defines deterministic tie-breaking by logical primary key `i.id ASC` (replacing baseline PostgreSQL's undefined quicksort tie order on `ORDER BY updated_at DESC` without a secondary key, and avoiding physical `ctid` drift across `UPDATE`/`VACUUM FULL`). `offset`/`limit` slicing computes `total` and page IDs (`<= 100`), and only the returned page fetches full `multiremi_issues` rows (with `closedFilterSql` plus an in-memory closed-status guard as defense in depth), labels (`hydrateIssues`), and the latest matching comment body (`ROW_NUMBER() OVER (PARTITION BY s.issue_id ORDER BY l.created_at DESC, l.seq DESC, l.id DESC) = 1`) for `extractSearchSnippet`. **Comment tie-breaking contract**: when multiple matching comments for the same issue have an identical `created_at`, both the SQL pushdown path and the non-ASCII fallback path deterministically order by `l.created_at DESC, l.seq DESC, l.id DESC` (picking the highest session sequence number first).
5. **Single read-snapshot isolation (`withIssueSearchReadSnapshot`)**: Both the SQL pushdown path and the non-ASCII workspace-scan fallback execute candidate discovery, `total`, page hydration, label hydration, and comment snippet retrieval inside one read snapshot (matching `IssuesRepo.listIssueStatusPages`):
   - Top-level calls open `BEGIN DEFERRED` on SQLite WAL (locks one WAL read mark without blocking concurrent `IMMEDIATE` writers) and `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY` on PostgreSQL.
   - Outer transaction reuse precondition (`db.inTransaction === true`): SQLite reuses the outer transaction directly (zero extra SQL); PostgreSQL checks `SELECT current_setting('transaction_isolation') AS iso` and only reuses outer `REPEATABLE READ` or `SERIALIZABLE` transactions, throwing an explicit contract error (`searchIssues inside an open PostgreSQL transaction requires REPEATABLE READ or SERIALIZABLE isolation`) if invoked inside a default `READ COMMITTED` transaction so cross-statement snapshot tearing cannot occur.
   - As defense in depth, `hydrateIssuesByIdsInWorkspace` also applies `closedFilterSql` and final page assembly enforces `if (!includeClosed && CLOSED_ISSUE_STATUSES.has(issue.status) && !issue.archivedAt) continue`.
6. **Reply-byte-budgeted comment pagination, BOM-safe outer PK body fetch & oversized-comment chunking (`postgresReplyMaxBytes()`)**: Both `searchIssueCommentSnippets` (SQL pushdown page snippets) and `scanIssueCommentsBounded` (non-ASCII/NUL fallback comment scan) enforce a per-SQL wire-byte budget derived from `postgresReplyMaxBytes()` (`ceiling - Math.max(512, Math.min(64 KiB, Math.floor(ceiling / 4)))`, floored at 256 B). `scanIssueCommentsBounded` also bounds its SQL `LIMIT ?` to `batchLimit = Math.max(2, Math.min(2000, Math.ceil(budgetBytes / 128) + 2))` (keeping `2000` under default 64 MiB while avoiding 2,000-row overlapping window sorts under tight budgets such as `4096 B` -> `batchLimit = 26`). Each batch estimates encoded JSON row size in SQL (`OCTET_LENGTH(to_json(COALESCE(...))::text)` across `body_md`, `issue_id`, `id`, and `created_at` on PostgreSQL; `LENGTH(CAST(COALESCE(l.body_md, '') AS BLOB)) * 6 + ...` on SQLite), omits `body_md` from the window CTEs (`latest_per_issue`/`batch`/`sized`), computes cumulative bytes via `SUM(row_bytes) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`, and in the outer `SELECT` projects `NULL` whenever `sized.cum_bytes > budgetBytes` (including `rn = 1`, marked `oversize = 1`, with `WHERE sized.rn = 1 OR (sized.cum_bytes - sized.row_bytes) <= budgetBytes` returning only the ~160 B metadata row when `rn = 1` exceeds the batch budget) and otherwise fetches `body_md` directly from the base table via correlated unique-index lookup `(SELECT l2.body_md FROM multiremi_conversation_log l2 WHERE l2.id = sized.id)` (preventing SQLite's VDBE window-materialization temp table from stripping a persisted leading `U+FEFF` on `>= 2048`-byte UTF-16 overflow rows and avoiding copying full bodies through window sorts). Continuation advances deterministically by cursor (`s.issue_id > lastIssueId` once an issue has matched, or exact lexicographical `(s.issue_id, l.created_at, l.seq, l.id)` continuation otherwise). Any single comment flagged `oversize = 1` is read via `readConversationLogBodyBounded(logId, isPostgres)`: PostgreSQL slices by Unicode code points via `SELECT SUBSTR(COALESCE(body_md, ''), ?, ?)` (`chunkChars = Math.max(16, Math.floor((Math.max(256, ceiling) - 192) / 6))`, advancing by `Array.from(chunk).length`), while SQLite slices raw database-encoded bytes via `SELECT SUBSTR(CAST(body_md AS BLOB), ?, ?) AS c, HEX(CAST('A' AS BLOB)) AS enc FROM multiremi_conversation_log WHERE id = ? AND body_md IS NOT NULL` (avoiding `COALESCE(body_md, '')` text-expression coercion; even `chunkBytes = Math.max(64, Math.floor((Math.max(256, ceiling) - 192) / 6) & ~1)`, advancing by `chunk.byteLength`), infers `utf-16le` (`"4100"`) / `utf-16be` (`"0041"`) / `utf-8` in the same query with zero extra SQL, and decodes once via `new TextDecoder(encoding, { ignoreBOM: true }).decode(Buffer.concat(chunks))` so embedded `U+0000`, multi-byte UTF-8 / UTF-16 surrogate pairs, leading `U+FEFF` (BOM), and leading `U+FFFE` code points are preserved identically to baseline. Every single bridge reply stays strictly below `postgresReplyMaxBytes()`. Workspaces strictly within single-batch capacity (`< batchLimit` comments, i.e. `<= 1999` under default budget, encoded batch size `<= budgetBytes`, and no single oversized comment) have `oversize = 0` (zero `SUBSTR` calls) and complete in 1 SQL round-trip per scan (`O(1)` reads within single-batch capacity; at exactly `2000` visible short comments under default budget `scanIssueCommentsBounded` executes 1 extra empty continuation probe before terminating); larger comment payloads or oversized bodies append bounded cursor-batch or `SUBSTR`-chunk reads decoupled from total issue count `N` (no per-issue N+1).
