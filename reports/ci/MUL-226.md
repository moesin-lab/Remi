## Why main backend(4) failed after #130

Sources: [baseline run 44303228674](https://github.com/moesin-lab/Remi/actions/runs/44303228674) at `19828d7e253ec1a6d79026f6eee951a6762f5251`; [failed run 44307088058](https://github.com/moesin-lab/Remi/actions/runs/44307088058) at `d188e8ddb`. Read both runs' backend-plan artifacts and the baseline shards 3/4 and failed shard 4 logs.

- The failed run was **main push**, not a PR. `scripts/ci-backend.ts`, `scripts/ci-backend-weights.json`, and backend run/service configuration were unchanged between these SHAs.
- Discovery grew from 898 to 899 files. Normal LPT redistribution moved `agent-task-snapshot-visibility.test.ts` from shard 3 to shard 4; hotspot tests stayed on shard 4. The new path-detector test went to shard 6. All eight estimated loads rose evenly from approximately 1392.63s to 1400.13s. This was not a changed weight or shard-count policy.
- The unchanged hotspot cases broadly took about 2.2–2.5 times their baseline wall time, including cases that still passed. Even the file-owned template migration rose from 3152.73ms to 5860.41ms. This supports runner/PG throughput variation rather than a specific query regression. Artifact/log data cannot establish the host's exact contention source.

Golden setup pins Date/PRNG, intentionally forcing a fresh database instead of cloning the migrated template (both runs: one fresh fallback, 13 clones). The other cases seed several large independent databases, or a 100-Chat fixture and multiple credentials. These costs are inside the test timer but outside measured query/byte windows. On the two 20s failures, the log's later `postgres bridge is closed` comes from credential insertion after timeout cleanup closes the database; it is secondary to the expired case budget.

Only these four failed cases now receive a **90s budget when PostgreSQL is configured**, matching the existing two large-fixture PG cases. SQLite budgets, dataset sizes, goldens, SQL counts, byte budgets, visibility and binding assertions remain unchanged. Setup emits database/store, seed and credential phase timings so the next real CI can confirm where its time goes. No production DB logic, global timeout, test concurrency or weights changed. This contains observed timing variability; precise runner contention and real PG regression validation remain open.
